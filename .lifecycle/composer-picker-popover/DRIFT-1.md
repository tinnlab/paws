# DRIFT-1 — implementation vs plan

Authored DURING phase 5, item by item, as each piece landed — not reconstructed
afterwards. Each entry is a real divergence between what PLAN.md said and what the
code does, plus how it was reconciled.

- **DRIFT-1.1** — verdict: impl-wins — **The primitive's trigger API changed shape.** The plan implied `triggerTestId` / `triggerLabel` / `triggerIcon` props; the shipped API takes a caller-rendered `trigger: ReactElement` (a `PlusMenuItem`), cloned to inject `aria-expanded`. Cause: the generated static testid registry only records literal `data-testid="…"` occurrences, so passing the id down as a prop silently DROPPED `assistant-menu-trigger` and `kb-menu-trigger` from the registry — the two ids ~10 existing e2e specs target — losing their compile-time typo check. Verified by regenerating and reading the diff, not by reasoning. ITEM-9's substance (both triggers use the ONE shared `PlusMenuItem` row) is unchanged and still asserted by TEST-9/TEST-18. PLAN.md's ITEM-1 wording was left as-is because it never fixed the prop shape; DECISIONS DEC-10 already anticipated the registry constraint.

- **DRIFT-1.2** — verdict: impl-wins — **A `defaultQuery` prop was added to `ComposerPickerPanel`.** Not in the plan. The FILTERED and NO-MATCHES states are reachable only by typing, which a mount-only gallery screenshot cannot do, so ITEM-11 was unbuildable without a seam. It is documented as gallery-only ("production callers leave it unset") and mirrors the repo's existing debug-seam pattern. Covered by the story's two cases (TEST-20).

- **DRIFT-1.3** — verdict: impl-wins — **ITEM-11's gallery work is TWO mechanisms, not one.** The plan named only a shard1 story. The state-matrix generator mints `ComposerPickerPopover:open` (from the controlled `<Popover open>`) and `:empty` as RequiredStates, and those are satisfied by a **delivery**, not by a story — so two `OverlayEntry`s were added to `src/modules/chat/gallery.tsx` alongside the story. Both were built rather than allow-listed with a `skip`, which is what keeps TEST-20 non-vacuous. PLAN's *Files to touch* amended.

- **DRIFT-1.4** — verdict: impl-wins — **`origin/main` is already RED on `npm run check`; the branch had to absorb it.** Not in the plan, and initially MISSED: the pristine-tree baseline run reported "exit code 0" in the task notification while the command's own `PIPESTATUS` was 1 — the `cmd | tail` trap the lifecycle skill warns about, and I read the notification instead of my own exit line. Re-measured on a `git stash`ed pristine tree: `check:testid-registry` exit 1 (registry missing 31 ids from citations / llm-provider / mcp-runtime) and `check:state-matrix` exit 1 (stale by 3 surfaces). Reconciled as a new **ITEM-12** with its own covering **TEST-21**, kept in a separate commit, with the 6 orphaned `stateCoverage` keys marked `skip` under an explicit "pre-existing, reconciled only to unstick the gate" reason rather than inventing coverage for features I did not build. Consequence recorded for the owner: the `sdk` submodule commit is deliberately NOT pushed.

- **DRIFT-1.5** — verdict: resolved — **`CSS.escape` removed from the active-option lookup.** The first implementation resolved the active row with `querySelector('#' + CSS.escape(id))`. The mounted harness crashed on it (`CSS` is undefined in jsdom), and `useId()` ids are not valid bare CSS selectors anyway, so this was a genuine portability bug, not a test-environment artifact. Replaced with `ownerDocument.getElementById(...)`. Caught by TEST-5/TEST-6 going red — exactly what the mounted harness exists for.

- **DRIFT-1.6** — verdict: none — **`kb-menu-search` is retired, as DEC-10 predicted.** The KB search box's testid is now derived (`kb-menu-options-search`). Re-verified that no spec references the old literal (`grep -rl kb-menu-search tests/` → nothing), so nothing breaks; the registry loses exactly that one id plus `assistant-selector` (deleted component).

- **DRIFT-1.7** — verdict: none — **Row markup moved from `role="button"` divs to a `listbox`/`option` pair**, per DEC-12. `aria-pressed` on KB rows is therefore replaced by `aria-selected`; checked that no e2e spec asserts `aria-pressed` on either picker (the only generic reader is `perf/live-audit-ui-conformance.spec.ts`, which tolerates its absence).

- **DRIFT-1.8** — verdict: none — **The lifecycle tier flipped LIGHT → HEAVY** (2 752 changed lines, dominated by the regenerated `STATE_MATRIX.md` from ITEM-12). The full audit flow applies rather than the single LIGHT round; noted so the phase-6/7 effort is not mistakenly scoped to the feature's own ~600 lines.
