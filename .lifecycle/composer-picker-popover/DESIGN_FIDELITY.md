# DESIGN_FIDELITY — composer-picker-popover

One verdict per invariant in PLAN.md `## Invariants`, lifted from
`docs/design/composer-picker-popover.md` §3.

- **INV-1** — fidelity: UPHELD — ITEM-2 bounds the panel at `w-auto min-w-60 max-w-80` and makes every row `min-w-0 flex-1 truncate` with the full label in `title`. The design's promise is that a long name is absorbed by the ROW, not by the panel; the plan realizes exactly that, and TEST-1 asserts it on a deliberately long name rather than on whatever names exist.
- **INV-2** — fidelity: UPHELD — ITEM-3 caps the list at `max-h-64` inside kit `ScrollArea axis="y"` (overlayscrollbars), copying the in-popover recipe at `kit/dropdown.tsx:80-84`. The design forbids a native scrollbar and an unbounded list; the plan adds no `overflow-y-auto` at all, so both halves hold. TEST-2 seeds 40 items and asserts the overlayscrollbars viewport exists and the panel is capped — it would fail on a native scroller.
- **INV-3** — fidelity: UPHELD — ITEM-4 renders the search box at the TOP of the panel unconditionally (deleting the KB `> 6` threshold, which is the concrete way the design's promise was violated on main), and ITEM-5 gives the no-match case an explicit "No matches." state kept distinct from the caller's zero-items CTA. TEST-3/TEST-4 cover filter-as-you-type and no-matches.
- **INV-4** — fidelity: UPHELD — ITEM-1 creates ONE primitive and ITEM-7/ITEM-8 make both callers thin. The plan additionally deletes the third, dead assistant picker (ITEM-10) so "one primitive" is true of the tree, not just of the two files the user named. TEST-5 is the structural acceptance test: it asserts neither caller file contains its own popover/scroll/search implementation and that both render the primitive.
- **INV-5** — fidelity: AT-RISK — the keyboard model itself (ITEM-6) is a straight port of the in-repo `VirtualMultiList` precedent and is low-risk, but **focus-on-open is not yet proven**: the kit `Popover` does not forward Base UI's `initialFocus`, and Base UI's own popup focus runs in a parent effect that may fire after the content's. This is recorded as a CONCERN on ITEM-6 in the plan audit. It passes phase 2 as AT-RISK rather than UPHELD, and the debt is discharged the only way it can be — by MOUNTING it (TEST-6 asserts `document.activeElement` is the search input, and TEST-13 drives the real popover in a browser), never by reading the code. If the race bites, the fallback is an `autoFocus`/`data-autofocus` attribute on the input, not a `setTimeout` hack.
