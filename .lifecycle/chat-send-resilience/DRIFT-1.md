# DRIFT-1 — implementation vs PLAN + design invariants

Written DURING phase 5, item by item, as each landed.

- **DRIFT-1.1** — verdict: impl-wins — PLAN's *Files to touch* and PLAN_AUDIT's ITEM-6 verdict both claimed `createLazyDispatcher` has "exactly one call site (`store-kit.ts:361`)". `tsc --noEmit` found **two more**, in the APP tree: `src-app/ui/src/api-client/lazy-dispatch.test.ts` (7 constructions) and `src-app/ui/src/api-client/shared-infra.test.ts` (1). They are tests of the SDK primitive that live in the app workspace, which is why a grep of `sdk/` missed them. Both are migrated to the two-stage signature (identity builder where the stage distinction is irrelevant). PLAN's *Files to touch* is amended to list them. This is `impl-wins`: the plan's claim was wrong about the codebase, not the implementation.

- **DRIFT-1.2** — verdict: plan-wins — while migrating those specs, one of them turned out to be a test that CERTIFIES the bug: `'a TRANSIENT chunk failure is retried — it does not brick the action'` failed the loader **exactly once**, which is the only case the shipped one-retry policy survived. It therefore asserted the design's property in its NAME while covering only the single case where the property happened to hold — the rig's actual scenario (a blip that outlasts one attempt, or any second failure in the session) was never exercised, which is how this defect shipped past a green suite. Per the plan's INV-2 ("a transient blip doesn't permanently brick a lazy action"), the spec is widened to fail through **two whole dispatch retry budgets** and still recover. The sibling `'a DETERMINISTIC resolve failure is memoized'` spec was throwing from the single combined loader — i.e. it was asserting the factory-throw policy while actually driving the chunk-download stage; it now drives the BUILD stage explicitly, which is what its own comment always said it was about. Both changes make the two specs mean what they claim.

- **DRIFT-1.3** — verdict: plan-wins — the existing `sendMessage.store.test.ts` fixture's default `stubRegistry()` composed `{ content: 'hello' }` with **no `model_id`**, so once ITEM-4's pre-POST guard landed, 11 pre-existing specs went red. The specs are about the in-flight latch and failure recovery, not about field validity, so the FIXTURE was wrong, not the guard: the default now composes `{ content: 'hello', model_id: 'm-1' }` (a valid body), and the three specs that deliberately compose an invalid body override it per test. Notable in its own right — the shared fixture had been modelling a structurally invalid request as the "normal" case.

- **DRIFT-1.4** — verdict: resolved — PLAN ITEM-4 said the guard replaces the `as any` "immediately before `ApiClient.Message.send`". Implemented slightly EARLIER: the validation runs right after composition (still inside the same pre-flight try), before `createConversation` and before the optimistic user bubble, so a rejected turn leaves no debris (no half-created conversation, no bubble to roll back) and the failure shares ONE handler with the contributor-failure path. The typed payload replacing `as any` is still at the POST site as planned. Same guarantee, strictly fewer side effects; PLAN ITEM-4's wording is amended to match.

- **DRIFT-1.5** — verdict: resolved — PLAN's *Files to touch* named `composeRequestFailure`-style helpers but did not anticipate that `registry.tsx` is JSX and therefore cannot be imported by a `node --test` spec (the repo's default unit runner cannot parse JSX). The composition algebra was extracted into a pure, JSX-free `composeRequestFields.ts` that `registry.tsx` delegates to — which is exactly the precedent this same directory already sets with `beforeSendCancel.ts` / `beforeSendCancel.test.ts`. PLAN's *Files to touch* is amended. The extraction means the unit specs test the helper, so the REGISTRY's delegation is proven separately by TEST-9 (real singleton registry) and TEST-13 (e2e) — recorded here so the "wired-and-behaving" question is not left implicit.

- **DRIFT-1.6** — verdict: none — the worktree could not resolve `@ziee/framework` at all with `node_modules` symlinked from the main repo (that repo's install predates `sdk/packages/*` being an npm workspace, so `node_modules/@ziee` there holds only `desktop-ui`/`ui-core`). A real `npm install` was run in the worktree instead; it links `@ziee/*` at THIS worktree's `sdk/packages/*`, which is also the only way the sdk edits under test are the ones being exercised. No product change; `package-lock.json` is unmodified.

- **DRIFT-1.7** — verdict: plan-wins — PLAN ITEM-7 said the listener should call `event.preventDefault()` "so a stale-deploy chunk miss stops surfacing as an unhandled page-level error". Implemented that way first; the e2e's TEST-14 leg then failed with `Couldn't prepare your message: the model (Cannot read properties of undefined (reading 'default')) chat extension failed.` Reading Vite's actual helper (`node_modules/vite/dist/node/chunks/node.js:28293`) explains it: `handlePreloadError` rethrows ONLY `if (!e.defaultPrevented)`, and the chain ends `baseModule().catch(handlePreloadError)` — so preventDefault makes the import promise **resolve with `undefined`** rather than reject. The plan's own invariant (INV-1: no silent invalid send) wins: the listener no longer preventDefaults, and ITEM-7 + DEC-3 are amended. Two additional hardenings landed with it: `lazy-dispatch.ts` now classifies a NULLISH module namespace as a failed IMPORT (retryable, never memoized) rather than letting it reach the build stage and be misfiled as a deterministic factory bug (TEST-6c), and TEST-11 now asserts the event is NOT preventDefaulted, with the mechanism written down. Worth noting: this was MY OWN fix reintroducing the exact defect class under audit, and only the end-to-end leg caught it — no unit test would have.

- **DRIFT-1.8** — verdict: impl-wins — with the e2e's other legs green, `pageErrors` was still non-empty: two uncaught `Failed to fetch dynamically imported module` errors that did NOT come from the send path (that rejection is handled) but from `store-kit.ts`'s baked-in boot PREFETCH. Its loop wrapped `lazyDispatchers[k].preload?.()` in a `try/catch`, which only catches a SYNCHRONOUS throw — `preload()` returns a promise, so a failed chunk became an unhandled rejection, i.e. a page-level error, for a warm-up nobody awaited. Added as ITEM-9 with the missing `.catch` (debug volume; ITEM-7's listener has already logged the load failure once). Same defect FAMILY as the branch's subject and squarely inside the design's Rank 2 ("no dynamic-import failure recovery anywhere"), so it is in scope rather than a scope creep. Only the e2e could have found it — no unit test observes an unhandled rejection at boot.

- **DRIFT-1.9** — verdict: plan-wins (invariant re-scoped, not dropped) — the e2e disproved the literal reading of TEST-14's first draft ("after the blip clears, the NEXT send succeeds without a reload"). Measured in-run: the retries after the first failure raise a fresh `vite:preloadError` each time but STOP HITTING THE NETWORK — once a module URL's fetch fails, the HTML module map records the failure for that URL and `import()` of the same specifier is not re-requested (2 aborted GETs vs 9 import attempts in the captured run). A bundler-rewritten static specifier cannot be cache-busted from the dispatcher, and auto-reload was rejected on data-safety grounds in DEC-3. INV-2 is therefore realized as: the dispatcher never ADDS its own permanent memo on top of the browser's (proved in-page by a THIRD send still producing fresh import attempts — under the shipped policy it had already latched and attempted nothing), and the user is told the one recovery that does work, which the spec then performs and asserts. The claim was narrowed to what is true and provable rather than left asserting a self-heal a browser cannot deliver.
