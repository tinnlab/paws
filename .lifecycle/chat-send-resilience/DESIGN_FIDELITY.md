# DESIGN_FIDELITY — chat-send-resilience

Does the plan REALIZE the design source's invariants, or reframe them?

- **INV-1** — fidelity: UPHELD — the design's promise has two halves and the plan carries both. "must not produce a silent invalid send": ITEM-1 makes `composeRequestFields` fail-closed, so a contributor failure can no longer return silently-incomplete fields, and ITEM-4's pre-POST required-field guard means even a non-throwing omission cannot reach the wire — no POST is issued at all, which is strictly stronger than "the 422 is explained." "Surface a user-visible, actionable error instead of a raw 422": ITEM-2 builds a message naming the failing extension, its cause, and the recovery step, and ITEM-3 puts it on `store.error` so it renders in the conversation error Alert on EVERY caller path (the two composers additionally toast it). The acceptance test (TEST-9) asserts the design's promise directly — zero send POSTs and an actionable, non-422 error surface — not merely that the new code runs.

- **INV-2** — fidelity: AT-RISK — *(downgraded from UPHELD at phase 7, on converging evidence from three independent blind agents plus a direct measurement; recorded rather than quietly relabelled.)* Both mechanisms the design names are implemented: the `vite:preloadError` handling (ITEM-7/ITEM-8) and the retry in `lazy-dispatch.ts` (ITEM-5/ITEM-6), and the dispatcher no longer adds a permanent memo of its own — pinned by TEST-6/TEST-6b, both verified RED under a deliberate reinstatement of the old policy. What is NOT fully deliverable is the literal "for the session" clause, and the reason is a platform invariant, not a shortfall in the implementation: per the HTML spec the module map records a FAILED fetch for a URL, so re-`import()`ing the same bundler-rewritten specifier does not re-request it for the life of that document. Measured directly in this branch's own e2e — 9 import attempts produced 2 network requests. The two ways to defeat that are a cache-busting specifier (impossible from the dispatcher: the specifier is generated by the bundler) and an automatic page reload (rejected in DEC-3 because it destroys an unsent composer draft and tears down an in-flight stream). So the delivered scope is: a transient failure is retried; it is never memoized by us; it is recorded as a stale build; and the user is told the one recovery that does work — which the e2e then performs and asserts. The `lazy-dispatch.ts` header states this limit explicitly instead of promising recovery the runtime cannot give. **This is a standing debt the orchestrator must see, not a silent reframing** — closing it properly needs a bundler-level retry seam (a cache-busted re-import), which is a separate design change.

- **INV-3** — fidelity: UPHELD — ITEM-4 deletes the `as any` at the POST site and replaces it with an explicit presence check for the fields the server declares required (`content`, `model_id`), placed immediately before `ApiClient.Message.send` — i.e. inside the `:85`→`:184` window the design says is unguarded. TEST-10 pins it as an acceptance test by driving a registry that returns fields WITHOUT `model_id` and yet throws nothing, so the only thing that can stop the invalid POST is the guard itself: if the guard were removed the test goes red even with ITEM-1 in place. That keeps the invariant proof independent of INV-1's mechanism rather than tautologically riding on it.
