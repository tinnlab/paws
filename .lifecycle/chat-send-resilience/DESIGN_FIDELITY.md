# DESIGN_FIDELITY — chat-send-resilience

Does the plan REALIZE the design source's invariants, or reframe them?

- **INV-1** — fidelity: UPHELD — the design's promise has two halves and the plan carries both. "must not produce a silent invalid send": ITEM-1 makes `composeRequestFields` fail-closed, so a contributor failure can no longer return silently-incomplete fields, and ITEM-4's pre-POST required-field guard means even a non-throwing omission cannot reach the wire — no POST is issued at all, which is strictly stronger than "the 422 is explained." "Surface a user-visible, actionable error instead of a raw 422": ITEM-2 builds a message naming the failing extension, its cause, and the recovery step, and ITEM-3 puts it on `store.error` so it renders in the conversation error Alert on EVERY caller path (the two composers additionally toast it). The acceptance test (TEST-9) asserts the design's promise directly — zero send POSTs and an actionable, non-422 error surface — not merely that the new code runs.

- **INV-2** — fidelity: UPHELD — the design names two mechanisms ("`vite:preloadError` handling and/or a retry in `lazy-dispatch.ts`") and one property ("a transient blip doesn't permanently brick a lazy action for the session"). The plan implements BOTH mechanisms (ITEM-7/ITEM-8 for `vite:preloadError`, ITEM-5/ITEM-6 for the retry) and pins the PROPERTY, not the mechanism: TEST-6 drives a loader that fails N times and then succeeds, and asserts a later dispatch succeeds — a test that would go red if the rejection were still memoized, regardless of which mechanism was implemented. The `MAX_RESOLVE_RETRIES = 1` permanent-memoization the triage identified is removed for the chunk-load stage specifically, which is the exact stage a "transient blip" hits.

- **INV-3** — fidelity: UPHELD — ITEM-4 deletes the `as any` at the POST site and replaces it with an explicit presence check for the fields the server declares required (`content`, `model_id`), placed immediately before `ApiClient.Message.send` — i.e. inside the `:85`→`:184` window the design says is unguarded. TEST-10 pins it as an acceptance test by driving a registry that returns fields WITHOUT `model_id` and yet throws nothing, so the only thing that can stop the invalid POST is the guard itself: if the guard were removed the test goes red even with ITEM-1 in place. That keeps the invariant proof independent of INV-1's mechanism rather than tautologically riding on it.
