# DECISIONS — github-token-fallback

Every human/product input the implementation needs, resolved up front.

### DEC-1: What evidence triggers the anonymous fallback — status+headers, or the response body's message?
**Resolution:** (amended at FIX_ROUND-1, revised again at FIX_ROUND-2) the **status**, plus ONE documented header. `401` ⇒ auth rejection; `403` + `X-GitHub-SSO` ⇒ auth rejection (a PAT not authorized for a SAML-SSO org); **every other `403`, and every other status, is not**. The body is never read.
**Why the first answer was wrong.** The original split `403` on the rate-limit headers. The phase-6 audit showed that cannot work: `x-ratelimit-*` rides on nearly every GitHub API response (so a non-zero `remaining` does not imply "not a rate limit"), and GitHub documents that a SECONDARY rate limit may arrive with no `retry-after` at all. Both gaps made a bare `403` classify as a rejection — spending the scarce anonymous budget AND telling the operator to replace a perfectly valid token. The distinction the brief asked me to consider is real and it does matter; the finding is that **headers cannot draw it**, and the only thing that could (the body's `message` prose) is not a contract and is the same brittleness INV-3 forbids for token shapes. The asymmetry decides it: NOT falling back on an exotic `403` leaves the pre-fix behaviour, which is no worse than today; falling back wrongly actively misleads.
**Basis:** convention — GitHub's REST API documents the `x-ratelimit-*` headers as the rate-limit contract, while the JSON body's `message` prose ("Bad credentials") is not a contract. Matching on prose is the same brittleness class INV-3 forbids for token shapes, one layer along. Headers also leave the `reqwest::Response` un-consumed, so the existing success and error paths in `list_releases` / `get_latest_version` are structurally untouched — a body read would have forced both to be restructured. The 403-without-a-rate-limit-header cases (revoked token, token lacking scope, SAML enforcement) are precisely the ones where an anonymous retry against a PUBLIC repo is likely to succeed, so classifying them as auth rejections is right on the merits, not just by elimination.

### DEC-2: Where does the anonymous retry live — inside the existing `MAX_ATTEMPTS` transient-retry loop, or as a separate one-shot?
**Resolution:** a separate one-shot. A `tried_anonymous` flag; on an auth rejection while authenticated, drop the header, set the flag, and re-issue WITHOUT consuming a transient attempt. Never more than one anonymous re-issue per call.
**Basis:** convention + codebase — the existing loop's `transient` predicate is explicitly 5xx-or-429 (`download.rs:502-505`), i.e. "conditions that may pass on their own". A credential rejection is not one: re-sending the same token is pure waste. And the anonymous budget is 60/hr/IP, so re-issuing anonymously more than once would double-spend a scarce resource to no benefit. Folding the two would also make the request-count assertions in TEST-3/4/5 untestable, which is itself the tell.

### DEC-3: How is the "invalid credential" state expressed on the wire — a new `source` variant, a reused `unavailable_reason`, or a new field?
**Resolution:** a new field `credential_status: "absent" | "used" | "unverified" | "rejected"` on the SAME `Catalog` → `AvailableUpdatesResponse` / `InstallableEngine` path that already carries `source`, `checked_at` and `unavailable_reason`. `source` keeps its exact prior meaning.
**Basis:** codebase — the two facts are orthogonal, and the existing UI proves it: `AvailableVersionsCard.tsx:103` derives `feedUnreachable = !!updateCheck?.unavailable_reason`, so setting `unavailable_reason` on a *successful* anonymous-rescued read would render "couldn't reach GitHub" over a card that is happily listing versions — a new false state, not a fix. A new `source` variant is worse: an anonymous-rescued catalogue genuinely IS `live`, and every existing `source === 'live'` consumer would silently stop matching. A field on the same struct is the "extend the vocabulary" reading; a log line or a separate endpoint would be the "parallel mechanism" the design forbids.

### DEC-4: The failing e2e — mock the releases API so the spec is hermetic, or let it exercise the real fallback?
**Resolution:** **let it exercise the real fallback** (`version-discovery.spec.ts` keeps hitting real GitHub, assertions unchanged), and put the hermetic proof at the **integration tier** against a loopback mock GitHub driven through the already-committed debug-only `LLM_RUNTIME_API_MIRROR` seam (TEST-3/4/5/6). Additionally harden the e2e (ITEM-9) so a genuine outage reports the server's own `source`/`unavailable_reason`/`credential_status` instead of "element not found".
**Basis:** convention + codebase, and the alternatives are not actually available. (a) `page.route()` API mocking is **forbidden by the repo rule** ("No `page.route()` API mocking — drive the real backend through the UI"), and it would prove nothing about the integration anyway — it would stub out the exact HTTP exchange the defect lives in. (b) Pointing the e2e's backend at a loopback mock would mean adding a backend-env seam to the SHARED `tests/fixtures/test-context.ts`, which violates B3 (never edit shared harness infrastructure to route around your feature's problem) — and the spec's own header comment already records that as ruled out. So (c) real is the only shape left for THIS spec.
**The tradeoff, stated:** the e2e depends on GitHub being reachable and on the anonymous 60/hr/IP budget not being exhausted — it can rot, exactly as warned. That is accepted **only because the burden is split by tier**: the fallback LOGIC (401→anonymous, 403-rate-limit→no retry, valid-token→stays authenticated, rejection→reported as rejection) is proven deterministically and offline by TEST-1..7, which never touch the network; the e2e's remaining job is the one thing a mock cannot do — prove the whole production path (real HTTP → real handler → real GitHub → real UI) actually works with a bad token in the environment. A mocked-everything spec would be green on a fix that never reached the wire. The rot risk is mitigated, not eliminated, by ITEM-9: a GitHub outage now fails with the server's own diagnosis, so it is distinguishable from a regression in one line of output instead of a bisect.

### DEC-5: What does the error/reason text say when a credential is rejected?
**Resolution:** name the env var and the status, never the value: `GitHub rejected the configured GITHUB_TOKEN (HTTP 401); retried anonymously: <outcome>`. The token string is never logged, never placed in an error, never serialized.
**Basis:** codebase — this is the pre-existing property of `github_token()`'s doc comment ("returned for immediate use in a header and is never logged, never placed in an error string, never serialized onto a response") and CODING_GUIDELINES §3. The fix must preserve it, and naming the VARIABLE is what makes the message actionable without leaking anything.

### DEC-6 (configurable-settings rule): is the anonymous fallback — or its retry count — an operational tunable that needs an admin settings row?
**Resolution:** **fixed**, not admin-configurable. The fallback is unconditional; the anonymous re-issue count is a named constant (`ANONYMOUS_RETRY_LIMIT = 1`), not an inline literal.
**Basis:** convention, with an explicit rationale as the rule requires. A toggle here would exist only to let an operator switch the defect back on — "fail hard when my credential is bad" is not a preference anyone holds, and the state it protects (`credential_status: "rejected"`) is already reported, so nothing is hidden by making it unconditional. The retry count is a rate-budget boundary (§DEC-2): making it operator-raisable would let a misconfiguration burn the 60/hr anonymous budget at 2×, 3×… per cache miss. Both are therefore the documented "security/budget boundary that must not be operator-weakened" exception. The one genuinely tunable knob in this area — how often the catalogue is refetched at all — **already exists** as the admin-configurable `release_cache_ttl` setting (the subject of TEST-10), so the tunable surface is not missing, it is already there.

### DEC-11 (added at FIX_ROUND-1): what is reported when a token was configured but GitHub never answered?
**Resolution:** a fourth value, `unverified`.
**Basis:** audit — the status was initialised to `used` from `token.is_some()` and only ever downgraded, so a total outage reported "GitHub accepted your token — 5000/hour" about a request GitHub never answered. `absent` would be a lie in the other direction (a token WAS configured). The honest answer to "does my token work?" after an outage is "we could not find out", and the whole feature is about not reporting states you did not observe. `used` is now promoted only after a real, non-rejecting response.

### DEC-7: Is `credential_status` optional (`skip_serializing_if`) or always present?
**Resolution:** always present (a plain `String`, no `skip_serializing_if`).
**Basis:** convention — `source` is already always-present for the same reason, while `checked_at`/`unavailable_reason` are skipped because *absence is meaningful* for them. Here absence is NOT meaningful: an omitted field would be indistinguishable from `"absent"`, which is a real, distinct state ("no token configured"). Skipping it would reintroduce the exact ambiguity INV-2 exists to remove.

### DEC-8: Does a cache hit report the credential status of the fetch that produced it, or `absent`?
**Resolution:** never `absent` by default — but the two cache paths differ, and the difference is deliberate. A **fresh hit** (inside the TTL, no upstream call made) echoes the verdict stored on the `Entry`. **Retain-on-failure** (a refresh was attempted and failed) reports the FAILED REFRESH's verdict, not the stored one.
**Basis:** codebase, amended during implementation (DRIFT-1.2). The fresh-hit rule mirrors `checked_at`, which is likewise echoed rather than recomputed — otherwise the rejection notice would flicker off on the second page load within the TTL, and an intermittent warning reads as a glitch. But applying the same rule to retain-on-failure would be a correctness bug in the opposite direction: when a token is REVOKED after an entry was cached, the failing refresh knows it was rejected while the stored entry still says `used`, and echoing the stale value would hide a live, actionable problem. Both halves are asserted in TEST-7.

### DEC-9: Does this branch also fix `voice`, `code_sandbox` and `server_update`, or extract a shared GitHub helper?
**Resolution:** **No** — surveyed and reported in `SURVEY.md` (findings S-1..S-5), not changed.
**Basis:** user — the brief says "report what you find even if you don't change it; a shared helper may be the right shape, but do not refactor broadly without saying so first." The survey states the case for the shared helper and its correct sequencing: `code_sandbox` and `voice` have no degradation vocabulary to report a `credential_status` INTO (S-1: `VersionStatus` has no `source`/`unavailable_reason` at all), so extracting the helper first would have nowhere to deliver its answer. Give them the vocabulary first, then extract.
