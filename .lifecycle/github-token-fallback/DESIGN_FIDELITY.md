# Design fidelity — plan vs DESIGN.md invariants

- **INV-1** — fidelity: UPHELD — ITEM-2 implements DESIGN §4's classification table as a pure `(StatusCode, &HeaderMap) -> bool`, and ITEM-3 makes an auth rejection re-issue the request once with no `Authorization` header instead of failing. The 403 split is explicit in the table (rate-limit ⇒ no fallback; anything else ⇒ fallback), so "they are different and the distinction matters" is realized as two different code paths, not one collapsed one.
- **INV-2** — fidelity: UPHELD — ITEM-1/5/6 add `credential_status` to the SAME `Catalog` → response structs that already carry `source` + `unavailable_reason`, travelling the same call path; `source` keeps its exact prior meaning. ITEM-4 additionally names the credential in the reason string on a failing request. No new endpoint, no log-only channel, no parallel struct.
- **INV-3** — fidelity: UPHELD — the classifier's inputs are status + response headers; it is structurally incapable of inspecting the token string, and no item anywhere validates a token's shape. The fallback is triggered by what GitHub ANSWERED.
- **INV-4** — fidelity: UPHELD — ITEM-3 sends the token first and only drops it after an observed rejection, so an accepted token yields exactly one authenticated request and `CredentialStatus::Used`. TEST-3 pins the request count (1) and the presence of the `Authorization` header, so a silent downgrade would fail rather than pass quietly.
