# DRIFT-1 — implementation vs PLAN.md and DESIGN.md

Authored DURING phase 5, item by item, as each landed — not reconstructed later.

- **DRIFT-1.1** — verdict: plan-wins — ITEM-3 was first implemented exactly as the plan worded it: `break-words` on the fallback `Text` elements inside `NotificationItem`'s `renderContent`. Driven live at 1440px it did NOT wrap: probing the rendered long-token row returned `overflowWrap: "normal"` and a text box 606.7px wide inside a 208px column. Two separate reasons, both invisible from reading the code: (a) the fallback block is not what renders these rows at all — ziee registers a renderer for every scheduler kind in `src-app/ui/src/modules/notification/kinds.tsx`, so `renderContent` returns `renderer.render(...)` and my edited branch is dead for the common case; (b) `break-words` (`overflow-wrap: break-word`) does not shrink a flex item's min-content contribution. Re-implemented to match the design's intent rather than the plan's wording: the wrap rule moved to the content COLUMN (which contains whatever any renderer emits, registered or not) as `wrap-anywhere` (`overflow-wrap: anywhere`), and the fallback `Text`s were reverted to their original form. Re-probed: `overflowWrap: "anywhere"`, text box 208px — contained. The plan's INTENT (ITEM-3 "make a long unbroken token wrap inside its row instead of forcing the row wider") is upheld; only its prescribed location was wrong, and PLAN.md's ITEM-3 wording ("the content column gets an explicit wrap rule on top of its existing `min-w-0 flex-1`") already named the column, so no plan amendment is needed.

- **DRIFT-1.2** — verdict: resolved — the first live measurement of the fix appeared to show it not working at all (panel still `w-72`, content still 350px, my new testids absent). Cause was environmental, not a code divergence: the worktree's `node_modules` was symlinked wholesale to the main repo's, so `@ziee/notification-ui` and `@ziee/kit` resolved to `/data/pbya/ziee/ziee/sdk/packages/*` — the MAIN repo's sdk — and the dev server was serving unmodified code. Rebuilt the worktree's `node_modules` as a real directory that links every package from the main repo EXCEPT the `@ziee` scope, which now points at this worktree's `sdk/packages/*`. Re-measured against the corrected server: the fix takes effect. Recorded because it is a live-verification trap, not because the implementation drifted.

- **DRIFT-1.3** — verdict: impl-wins — the plan and TESTS.md phrased INV-4's containment check as "no interactive control paints outside the panel's box", which the first e2e draft asserted on all four edges. Driven live, 4 of 17 controls at 1440px and 7 of 17 at 320px sit outside the panel's VERTICAL bounds — correctly, because ITEM-2 makes the list a scroll container, so a row below the fold is legitimately clipped. Only HORIZONTAL escape is the reported defect (buttons drawn over the page beside the panel). Narrowed both the e2e assertion and TESTS.md's TEST-3 wording to the x-axis, and stated the reason in the spec so a future reader does not "restore" the four-edge form and get a permanently red test. Re-measured horizontally: 0 of 17 outside at 320 / 390 / 1440.

- **DRIFT-1.4** — verdict: impl-wins — TEST-4 as planned asserted the list is scrollable via `scrollHeight > clientHeight` on the list element. `ScrollArea` (overlayscrollbars) moves the actual scrolling to an inner viewport node, so the host element reports `scrollHeight === clientHeight === 416` and the planned assertion would have passed vacuously on a NON-scrolling list. The spec now reads the `[data-overlayscrollbars-viewport]` child (measured 520 vs 416 at desktop, 540 vs 270 on a short 360×480 viewport). Same assertion, correct node.
