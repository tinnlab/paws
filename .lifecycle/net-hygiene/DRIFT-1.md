# DRIFT-1 — implementation vs plan (authored during phase 5, item by item)

- **DRIFT-1.1** — verdict: impl-wins — PLAN put the lazy-dispatch fix inline in `store-kit.ts` (ITEM-4). Implemented it there first, then found the resulting code was untestable: `store-kit.ts` transitively imports zustand + `./events` + `./stores`, so a `node --test` spec dies on module resolution before any assertion (the reason the pre-existing `sdk/packages/framework/src/store-kit.test.ts` cannot run at all today). Extracted the dispatcher to a dependency-free `sdk/packages/framework/src/lazy-dispatch.ts` and had store-kit consume it. Same behaviour, genuinely unit-testable (TEST-4 drives a real guarded action through both the cold and the steady-state path), and better modularity. PLAN's `## Files to touch` amended to include it.
- **DRIFT-1.2** — verdict: impl-wins — same shape for ITEM-9: `reconnectDelayMs` was written inside `SyncClient.ts`, which imports `../api-client/core` and `../events/store`, so TEST-8 could not reach it. Extracted to `sdk/packages/framework/src/sync/backoff.ts` (carrying `INITIAL_BACKOFF_MS` / `MAX_BACKOFF_MS` with it, so the constants live next to the policy that uses them). PLAN amended.
- **DRIFT-1.3** — verdict: impl-wins — ITEM-6 planned `hasLiveSession` as a helper inside `modules/loadContext.ts`. `loadContext.ts` imports the Auth store, so TEST-6 pulled the whole store graph. Moved the predicate into a dependency-free `modules/liveSession.ts` (loadContext imports it), and renamed the spec `liveSession.test.ts`. The predicate is the thing under test, so this is where it belongs.
- **DRIFT-1.4** — verdict: impl-wins — a defect the plan did not anticipate, found by MEASURING rather than reading: after ITEM-5 moved the boot verification earlier, `/` still fired `/api/auth/me` twice (t≈59 ms and t≈381 ms). `AuthGuard`'s mount effect calls `initAuth()` as the backstop, and by the time the guard mounts the boot call has already RESOLVED, so `isLoading` is false again and the existing guard does not hold. Extended ITEM-7's freshness predicate to `initAuth` (`if (state.isAuthenticated && isMeFresh()) return`). Re-measured: 1 `/auth/me` per cold load on all three probed routes. This is exactly the class of thing "verify by running, not by reading" exists for.
- **DRIFT-1.5** — verdict: resolved — the unit specs needed three test-resolver capabilities that did not exist: `@ziee/*` subpath resolution, extensionless relative resolution inside the sdk, and a stub for the `permissions` barrel (which re-exports `Can.tsx`; node's type-stripping runtime cannot parse JSX). Added all three to `src-app/ui/scripts/node-test-hooks.mjs` + `sdk/.../__test-stubs__/permissions.ts`. **This is a SHARED harness edit (rule B3), so it was scoped deliberately:** the relative-resolution fallback applies ONLY to parents inside `sdk/packages/*`, so no app spec's resolution — including its failure signature — changes. Verified by comparing the full `npm run test:unit` output against the unmodified base worktree: the SAME 12 specs fail, for the SAME reason (`ERR_MODULE_NOT_FOUND` on `./Auth.store`), before and after. It is a capability gap in the harness, not a workaround for this feature.
- **DRIFT-1.6** — verdict: none — ITEM-10 landed as planned but is confirmed INERT: a repo-wide search shows `state.stores` is read by nothing outside `module-system/store.ts` itself (the global `Stores` facade was removed), so the second proxy was never accessed and never ran `init`. PLAN_AUDIT already flagged this and DEC-12 recorded it; no request reduction is attributed to it in the results.
- **DRIFT-1.7** — verdict: none — `check:state-matrix` fails on the UNMODIFIED base worktree (verified), i.e. the committed state matrix was already stale. Regenerating it (required, since ITEM-7's comment block shifts `AuthGuard`'s line numbers) also pulls in ~170 unrelated line-number updates. Recorded so the reviewer does not read that hunk as scope creep: it is a mechanically-generated file being brought back in sync, and it is what makes `npm run check` green.
- **DRIFT-1.8** — verdict: none — PLAN assumed `settings-user`'s ≈1,150-request figure would be materially reducible here. Measurement says otherwise and the plan's own DESIGN §6 predicted it: the cell is ~13 COLD BOOTS (the audit's `nav()` uses `page.goto`), and per boot the dominant term is the by-conversation N+1 — explicitly out of scope. This branch removes ~2 requests per boot plus the per-step duplicate `sync/subscribe`, giving 428 → 398 on that cell. Not a drift in the implementation; recorded so the RESULTS do not overclaim.
- **DRIFT-1.9** — verdict: none — the audit's `waterfall` DEPTH did not improve the way PLAN implied it would (14 → 12 findings; max depth 24 → 20). Root cause established by measurement: the detector counts a run of consecutive requests each starting after the previous ended, and the 19-request by-conversation N+1 is inherently such a run, so it dominates and destabilises the figure (single-run depths on `/settings/general` ranged 5–25 across repeats of the SAME build). The invariant INV-2 actually asserts — that requests which do not depend on a predecessor are issued concurrently — is proven by the deterministic metric instead: `/api/auth/me` starts at 63–77 ms instead of 361–377 ms, and OVERLAPS `/api/app/setup/status` on every probed route (it did not on `/settings/profile` before). TEST-5 asserts the overlap, not the depth, for exactly this reason.
