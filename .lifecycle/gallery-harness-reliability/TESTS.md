# TESTS — gallery-harness-reliability

Every ITEM is covered by ≥1 TEST; every `INV-N` is pinned by ≥1 `[acceptance]`
test that asserts the DESIGN's promise (not the implementation's behaviour).

**Runner note (repo-specific, easy to get wrong):** in the UI workspace vitest
collects only `*.store.test.ts` / `*.test.tsx` — a plain `*.test.ts` runs NOTHING
and reads like a pass. Every unit test below is therefore a `*.test.mjs` executed
by `node --test`, wired into a real npm script by ITEM-21, and its PASS is recorded
from that script's own exit code.

## Acceptance tests (design-invariant proofs)

- **TEST-1** (tier: e2e) [acceptance] [invariant: INV-1] [covers: ITEM-1, ITEM-2] file: `sdk/packages/gallery/scripts/lib/quiesce.e2e.mjs` — asserts: the CAUSE is fixed, not masked. Driven with the muting classifier **forced off** (`GALLERY_NO_HARNESS_MUTE=1`), a full crawl over the real gallery produces **zero** `net::ERR_NETWORK_CHANGED`/`net::ERR_ABORTED` cancellation artifacts and zero `Failed to fetch dynamically imported module` crashes. A build that shipped only the ITEM-3/4 muting arm FAILS this test, because the muting is disabled while it runs — which is precisely the "reachable layer" INV-1 forbids substituting for the cause fix.
- **TEST-2** (tier: unit) [acceptance] [invariant: INV-2] [covers: ITEM-8] file: `sdk/packages/gallery/scripts/lib/finding-classify.test.mjs` — asserts: a HIGH finding seen in 2 of 3 repeats is annotated `flaky: true` and **subtracted from the gating total**, while one seen in 3 of 3 gates; and that at `repeat === 1` NO finding is ever annotated `flaky` (a single run cannot distinguish stable from flaky, so the invariant's "reproduce across runs before it gates" must not silently downgrade a one-run finding).
- **TEST-3** (tier: e2e) [acceptance] [invariant: INV-3] [covers: ITEM-10, ITEM-11] file: `sdk/packages/gallery/scripts/lib/host-lock.e2e.mjs` — asserts: two `gate:ui` invocations started concurrently from DIFFERENT worktrees on this host do not overlap. The second prints a visible "waiting for <holder worktree> pid <N>" line and its crawl begins only after the first releases. Negative control in the same proof: with `GATE_UI_LOCK=0` the two DO overlap, confirming the lock is what serialized them and not incidental timing.
- **TEST-4** (tier: e2e) [acceptance] [invariant: INV-4] [covers: ITEM-12, ITEM-13] file: `sdk/packages/gallery/scripts/gate-ui.stale.e2e.mjs` — asserts: given a pre-existing `RUNTIME_FINDINGS.jsonl` describing an all-clean 106-surface run, a `gate:ui` whose runtime-health child is KILLED mid-crawl exits non-zero, prints an explicit incomplete-run reason, and prints **no per-surface verdict table at all**. Directly falsifiable: the pre-seeded file says "all clean", so a gate that inherited it would print a PASS table — the test asserts that table's ABSENCE.
- **TEST-5** (tier: unit) [acceptance] [invariant: INV-5] [covers: ITEM-14] file: `sdk/packages/gallery/scripts/gen-testid-registry.test.mjs` — asserts: on a fixture containing (a) a line comment naming `data-testid="phantom-from-line-comment"`, (b) a JSDoc block naming `data-testid="phantom-from-jsdoc"`, (c) a template interpolation `` `[data-testid="${CONST}"]` ``, (d) a self-referential comment warning that a scanner would harvest the pattern, and — as the **negative control** in the SAME fixture — (e) a REAL `<div data-testid="real-attribute-id" />` plus (f) a real `data-testid={x ?? 'real-fallback-id'}`, the collector returns EXACTLY `{real-attribute-id, real-fallback-id}`. The four phantoms are absent because comments are not AST nodes, and the two real ids are present — so the test fails both a scanner that still harvests comments AND one that fixes phantoms by dropping real ids.
- **TEST-6** (tier: unit) [acceptance] [invariant: INV-6] [covers: ITEM-18, ITEM-20] file: `sdk/packages/gallery/scripts/check-harness-parity.test.mjs` — asserts: the parity guard REPORTS A VIOLATION when a behavioural core (quiesce, run-manifest, host-lock, flaky-classification) is present in the sdk copy but absent from `src-app/desktop/ui/scripts/`. Proven by mutating a temp copy of the desktop script to remove one core and asserting the guard goes red — i.e. the guard is shown to actually catch the "fix lands in one place and not the others" failure, not merely to pass today.
