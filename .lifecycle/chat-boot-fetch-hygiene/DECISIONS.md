# DECISIONS — chat-boot-fetch-hygiene

Every human/product input this round needs, resolved up front.

### DEC-1: Which of the two `/chats` mount fetchers becomes the single owner — the page or the list?
**Resolution:** `ChatHistoryPage` (the route page) owns the fetch; `ConversationList`'s mount effect is removed and the list becomes a consumer of store state.
**Basis:** codebase — `ConversationList` has exactly ONE production import site (`ChatHistoryPage.tsx:5`; verified by repo-wide grep over `src-app/ui/src` + `src-app/desktop/ui/src`), so it can never mount without the page and can never mount FIRST (the page renders it only once `conversations`/`loading`/`error`/`hasSearch` is truthy, all of which are consequences of a load). The page is therefore the only owner that covers 100% of the cases, including the empty state where the list never mounts at all — which is exactly why the page's effect was added in the first place (see its `:56-60` comment). Removing the page's effect instead would reintroduce the empty-state bug that comment documents. This also matches `agent-kit/docs/CODING_GUIDELINES.md` §12: a component consumes store state; the route owner drives the load.

### DEC-2: Do we implement the triage's Rank-4 suggestion — fire the second-tier boot fetches optimistically and tolerate a 403?
**Resolution:** **No.** Descoped as ITEM-5; the `hasPermissionNow` self-gates stay exactly as they are, and the reasoning is recorded (DESIGN.md §"Rank 4") plus pinned by an executable test (TEST-5).
**Basis:** convention — this repo states the **no-403 rule** as a standing invariant in `CLAUDE.md` §"Realtime Sync → Frontend" ("the store SELF-GATING its refetch … the perm checked MUST equal the read-perm the refetch endpoint enforces") and again in `agent-kit/docs/CODING_GUIDELINES.md` §7; the SDK's own notification store calls it "the no-403 invariant" in its doc-comment (`sdk/packages/notification-ui/src/store/index.ts:15-16`). The dependency is real, not incidental: `hasPermissionNow` reads `authStoreProxy().$.permissions` (`sdk/packages/framework/src/permissions/hasPermissionNow.ts:18`), which only `GET /api/auth/me` populates — so there is nothing to "parallelize", the input genuinely does not exist earlier. And the cost is concrete rather than theoretical: `server_update::` is granted by NO migration under `src-app/server/migrations-merged/`, so it reaches only administrators via `*`; dropping that gate would put a guaranteed 403 on the boot path of every ordinary user, to save ≈ one RTT on a LOW-severity finding. That is a regression dressed as an optimization.
- DESCOPED: ITEM-5 — implementing it would violate INV-3, a documented standing rule of this codebase, and would put a guaranteed 403 on every non-admin boot to save ~1 RTT; the correct outcome for this LOW finding is a documented no-change backed by TEST-5 [approved: brief author / orchestrator brief, 2026-07-28 — "If the serialization is genuinely intentional and load-bearing … then the correct outcome is to document why and leave it alone … do not manufacture a change"]

### DEC-3: Is the `onboarding` store's identity gate (`watch(useAuthStore, s => s.user?.id, …)`) also left alone?
**Resolution:** Yes — unchanged, same disposition as DEC-2, though for a different reason.
**Basis:** codebase — `GET /api/onboarding/progress` is JwtAuth-only (no permission), so unlike server-update it *could* technically fire on a bare persisted token. It is still left alone because the gate is not a permission check but an **identity-change subscription**: the same `watch` that fires the initial load is what clears stale progress and refetches on a user SWITCH (`onboarding/stores/onboarding/index.ts:19-30`, which explicitly documents watching the user ID rather than `isAuthenticated` for exactly that reason). Firing optimistically would mean either duplicating the fetch (once optimistically, once on the identity settling) or unpicking the switch-safety — trading a correctness property for ≈1 RTT, which INV-1 forbids ("a stale/missing refetch is worse than a duplicate"). The predecessor lifecycle already made the analogous call and DESCOPED its own ITEM-6 (deriving `isAuthenticated` from a live persisted token) on trust-boundary grounds; re-litigating it here at LOW severity would contradict that reviewed decision.

### DEC-4: Should the measurement be a throwaway script or a committed test?
**Resolution:** A committed e2e spec (`chats-list-single-fetch.spec.ts`), which serves as both the measurement and the regression guard.
**Basis:** convention — the predecessor `net-hygiene` lifecycle did exactly this (`tests/e2e/perf/boot-parallelism.spec.ts` is a committed measurement-as-assertion, and its `boot-probe.mjs` harness is committed alongside). A throwaway measurement would leave the fix unguarded, so the duplicate could silently return.

### DEC-5: Does this round introduce any operational tunable (limit, timeout, retention, toggle) needing an admin-configurable settings row?
**Resolution:** No — the change introduces **zero** tunables. It deletes a React effect and adds two specs. No constant, threshold, cap, timeout, retention period, or feature toggle is added in either direction.
**Basis:** convention — the configurable-settings rule applies to introduced tunables; there are none. Pre-existing values the specs merely *read around* (the store's `limit`, the transport's coalescer window, `ME_BOOT_FRESH_MS`) are owned by the predecessor lifecycle and are not touched.

### DEC-6: Does this round need a `desktop/ui` twin change?
**Resolution:** No.
**Basis:** codebase — neither `src-app/desktop/ui/src/modules/chat/components/ConversationList.tsx` nor `.../pages/ChatHistoryPage.tsx` exists; the desktop workspace does not carry a hand-written override of either file. R2-3 (diff-review desktop overrides for dropped security logic) is a verified no-op for this diff, not an omission.

### DEC-7: What is the acceptable outcome if the measurement shows only ONE request on the unmodified tip (i.e. Rank 3 is already a non-issue)?
**Resolution:** Report it plainly as a non-issue and make NO production change; the spec still lands as the regression guard, and PLAN/DRIFT record the `impl-wins` reconciliation.
**Basis:** user — the orchestrator brief states "If either turns out to be a non-issue on the merged tip, say so plainly; a well-evidenced 'no change needed' is a complete and acceptable outcome for a LOW finding." Recorded here up front so the measurement cannot be rationalized into justifying a change after the fact.
