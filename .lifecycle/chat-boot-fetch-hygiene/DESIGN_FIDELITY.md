# DESIGN_FIDELITY — chat-boot-fetch-hygiene

One verdict per invariant in `PLAN.md` §Invariants.

- **INV-1** — fidelity: UPHELD — the plan's only behavioural change (ITEM-2) removes a *redundant second caller*, never a load-bearing refetch: the removed effect provably cannot be the first caller (`ConversationList` renders only once the page's own fetch has already flipped `loading`/`conversations`/`error`), and every post-mutation refetch path (`bulkDelete`, `deleteConversation`, `setSearchQuery`, `setSort`) is untouched. ITEM-3 exists specifically to prove "fewer requests did not cost data", and TEST-3 drives the exact case the removed comment cited (a conversation created AFTER the store was primed) rather than arguing it from the code. The plan also explicitly refuses the *other* direction of this trade: ITEM-5 is descoped because firing optimistically to save a round-trip would regress correctness for a permission-less user.

- **INV-2** — fidelity: UPHELD — ITEM-2 is exactly this invariant applied: two independent callers of the same route-level fetch collapse to ONE owner (the page), with the child consuming shared store state instead of issuing its own load. It reduces caller count at the source rather than leaning harder on the downstream in-flight coalescer, which is what the invariant asks for ("one shared store read … rather than N independent callers"). ITEM-1 pins the claim to a measured before/after wire-request count rather than a structural argument.

- **INV-3** — fidelity: UPHELD — the plan makes NO change to any `hasPermissionNow` self-gate. It goes further than passive compliance: ITEM-4 records the verdict that the gates encode a real dependency, ITEM-5 explicitly descopes the triage's "fire optimistically, tolerate a 403" suggestion for violating this invariant, and TEST-5 turns the invariant into an executable assertion (a restricted user's boot issues ZERO requests to the permission-gated endpoint) so a future round cannot silently drop the gate and stay green.
