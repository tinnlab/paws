# DRIFT-1 — implementation vs plan (authored during phase 5)

Reconciled item by item as each landed, against BOTH the plan and the design's
invariants. Evidence for every entry is in `MEASUREMENTS.md`.

- **DRIFT-1.1** — verdict: resolved — **The triage's stated mechanism for Rank 3 was wrong, and the plan was right to treat it as a hypothesis.** The triage said "only the transport coalescer prevents a duplicate wire request" — i.e. the duplicate never reached the network. Measured on the unmodified tip: **3** `GET /api/conversations` from the `/chats` document, all serial. The coalescer does absorb the page ⇄ sidebar pair, but it cannot touch a `reloadQueued` replay (which starts only after the first request has completed) or a debounce firing 500 ms later. PLAN.md ITEM-1 existed precisely to test this before changing anything, and DESIGN.md §"Rank 3" already flagged the claim as "a hypothesis to test, not a given". No plan change needed; the design's framing held.

- **DRIFT-1.2** — verdict: impl-wins — **A THIRD redundant caller existed that neither the triage nor the plan named.** After removing `ConversationList`'s mount fetch (ITEM-2), the count went 3 → **2**, not 3 → 1. Call-stack attribution identified the survivor: `ConversationList`'s 500 ms search debounce also runs on mount and calls `setSearchQuery('')` when the store's query is already `''`, and `setSearchQuery` unconditionally issues `loadConversations(1)`. This is the same defect class as ITEM-2 (a redundant independent caller of the route-level fetch) and is squarely inside INV-2, so it is fixed rather than noted: **PLAN.md amended with ITEM-6**, **TESTS.md amended with TEST-6** (covering the risk ITEM-6 introduces — that the guard breaks real search), coverage map updated, phases 1–3 re-gated. Final measured count: **1**. Had this been left, TEST-1's `=== 1` assertion — the executable form of INV-2 — would have been unachievable, and the honest outcome would have been to weaken the invariant's test. Fixing the cause was cheaper and truer than relaxing the assertion.

- **DRIFT-1.3** — verdict: impl-wins — **The planned measurement instrument was not accurate enough and had to be replaced.** PLAN §"Patterns to follow" said to mirror `boot-parallelism.spec.ts`'s `recordApi` helper (Playwright's `page.on('request'|'response')`). That helper over-counts across a navigation: it also catches requests the PREVIOUS document had in flight. It reported 3 both before AND after the ITEM-2 fix, which would have led to the false conclusion that the fix did nothing. Replaced in `chats-list-single-fetch.spec.ts` with a **passthrough `window.fetch` observer** installed via `addInitScript`, recording `location.pathname` so calls are attributable to the `/chats` document; requests still reach the real server, so this is an observer, not a mock. `boot-tier-permission-gate.spec.ts` keeps the original `recordApi` helper — it compares two endpoints *within* one boot, where the contamination is irrelevant. PLAN/TESTS prose amended to record the divergence and its reason, so nobody "simplifies" the instrument back.

- **DRIFT-1.4** — verdict: resolved — **TEST-6's first draft asserted nothing.** It used an unscoped `page.getByText(beta)` to assert the filtered-out conversation was gone; it went red because the SIDEBAR's recent-conversations widget renders the same titles from a separate, deliberately unfiltered `recentConversations` cursor. The red was correct and useful: unscoped, the assertion could never have distinguished "search filtered the list" from "search did nothing". Scoped to the `chat-conversation-list-rows` container; re-run PASS.

- **DRIFT-1.5** — verdict: none — **A pre-existing broken unit test, not caused by this branch.** `src/modules/chat/stores/ChatHistory.store.test.ts` fails to run (`TypeError: registerLazyStore is not a function`). Verified pre-existing by stashing all `src-app/ui/src` changes and re-running on the untouched base at `9363976a2` — identical failure. Not in this round's enumerated set (all 6 TESTs are `tier: e2e`), out of scope to fix here, and reported upward rather than silently absorbed.

- **DRIFT-1.6** — verdict: none — **Environment, not code.** The worktree initially borrowed `node_modules` by symlink from `/data/pbya/ziee/ziee`, which sits on `feat/array-streaming` — a branch whose `sdk` submodule has no `store-kit`, so `@ziee/framework/store-kit` failed to resolve. Replaced with a real `npm install` in this worktree so every gate resolves against THIS branch's SDK. Recorded because it briefly looked like a code failure and would mislead anyone reproducing these runs.
