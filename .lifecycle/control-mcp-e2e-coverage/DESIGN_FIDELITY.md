# DESIGN_FIDELITY — control-mcp-e2e-coverage

One verdict per `PLAN.md` `## Invariants` entry, judged against
`DESIGN.md` (§2–§5) rather than against the plan's own framing.

- **INV-1** — fidelity: UPHELD — the design's charge is that this area is "covered" by tests that never execute. The plan attacks that structurally, not cosmetically: ITEM-12 removes the vendor-key gate, ITEM-17 adds an executable guard so it cannot be reintroduced, ITEM-8 replaces a stub-only title assertion (which passes while production is broken) with a real-model assertion, and ITEM-4 asserts the exact live-session query end-to-end. Phase 8 records the real RUN of each, so "it passed" and "it ran" are separately evidenced.
- **INV-2** — fidelity: UPHELD — ITEM-9 (Rust) and ITEM-11 (TS) resolve the configured test LLM from ANY of the OpenAI seam, the Anthropic seam, or the global `ZIEE_TEST_LLM_BASE_URL`, returning `None` only when nothing at all is configured; ITEM-10/12 re-gate on that. ITEM-17 pins it so a future edit that narrows the gate back to one vendor fails a test.
- **INV-3** — fidelity: UPHELD — ITEM-13's prompt is "create a new project called <Foo>" with the operation id deliberately absent, and the assertion is on the RECORDED `list_capabilities` tool call (`GET /api/mcp/tool-calls?conversation_id=…`), so the test proves discovery happened rather than assuming it. A test that merely reached the approval card would NOT satisfy this — the discovery assertion is separate and would fail if `list_capabilities` returned 0 again.
- **INV-4** — fidelity: UPHELD — every approve/deny row (ITEM-13/14/15) drives a FRESH chat, which is auto-approve by default, and asserts the approval card appeared for the mutating invoke. The existing production rule (`control_call_needs_approval` → `policy::is_mutating`) is what is under test, not re-implemented in the spec.
- **INV-5** — fidelity: UPHELD — every approve leg verifies through the REST API (`GET /api/projects`, `GET /api/assistants`, `GET /api/memory/settings`), never through the chat DOM; every deny leg verifies the SAME REST surface shows nothing created.
- **INV-6** — fidelity: AT-RISK — the design says "the op is not offered/denied". Verified against the catalog: `Project.create` and `Assistant.create` declare no `**Required Permission:**` in their handler docs, so `Operation.required_permission` is `None` and the control surface's per-user filter cannot hide them — for those ops only the "denied" half is assertable (the forwarded-JWT loopback 403). ITEM-16 therefore covers BOTH halves explicitly: **not offered** via `MemorySettings.update` (`memory::write`, which IS declared) and **denied + nothing created** via `Project.create`. The residual risk — that the catalog's permission filter is a no-op for many mutating ops — is a pre-existing catalog-precision gap (security is still enforced by the real route) and is recorded rather than silently absorbed; it is resolved to a covered state by DEC-5 and must be re-checked by the phase-6 `design-conformance` angle.
- **INV-7** — fidelity: UPHELD — ITEM-1 implements exactly "tokenize on whitespace and require ALL terms to match (each term may match any field)"; ITEM-2 implements "order results by relevance so `Project.create` ranks first for 'create project'"; ITEM-3 pins "keep single-term behavior at least as good as today" as a direct unit assertion, and the design's exact failing query is a named test case. The matcher is unit-tested DIRECTLY (pure fns), which is the design's explicit demand ("not just through the MCP"), with ITEM-4 as the through-the-MCP companion.
- **INV-8** — fidelity: UPHELD — ITEM-8 is a real-LLM test asserting a conversation ends TITLED. It fails if titles stop being generated, and — unlike the existing stub tests — it would have FAILED on the shipped code, because the bug is a property of a real reasoning model's token accounting that a stub cannot express. ITEM-7's stub-level retry coverage is a complement, never the anchor.
