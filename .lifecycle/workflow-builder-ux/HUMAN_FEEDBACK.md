# HUMAN_FEEDBACK — workflow-builder-ux

The feature originated in owner feedback on the running app. Recorded verbatim
from the task brief; the branch has not yet been re-reviewed by the owner.

- **FB-1** [status: resolved] — "the Tool field is a free-text input with placeholder 'e.g. search' — the user has to know the exact tool name; it should be a picker populated from the selected server's actual tools" → the Tool control is a `Combobox` over `GET /api/mcp/servers/{id}/tools`, with a stated-reason fallback to hand entry when the server can't be reached. [generalizable: yes — an entity reference the system can enumerate is NEVER a free-text field; pin it with a CLASS test that scans every form for the rule, not an instance test on the one field fixed]
- **FB-2** [status: resolved] — "Arguments is a raw key/value editor where the user invents keys; once a tool is chosen its input schema is known, so the arguments should be a generated form" → arguments are generated from the tool's declared `input_schema`, one typed control per property with requiredness/description/default, local `$ref`/`$defs` resolved, schema-undeclared keys preserved in an "Additional arguments" section. [generalizable: yes — collect a structured value from a form generated from the target's DECLARED schema; a raw key/value or JSON box is a last-resort fallback that must state why it is being shown]
- **FB-3** [status: resolved] — "'step has neither prompt: nor prompt_file:' is developer-speak that names YAML keys; the user has no idea which step it refers to" → all 41 validator codes get author-facing copy at the presentation boundary (the backend keeps its machine-readable codes), and a backend test fails the server suite if a code has no copy. [generalizable: yes — humanise at the PRESENTATION boundary keyed off a stable machine code, and make an un-humanised code a build failure rather than a review item]
- **FB-4** [status: resolved] — "the error is not attributed to a step — the panel is at the bottom while a different step is selected" → every finding renders "Step N · <label>" and is a button that selects its step; the step list marks which steps are broken. [generalizable: yes — a diagnostic must name the entity it concerns AND navigate to it; a page-level list of findings about per-item state is a defect]
- **FB-5** [status: resolved] — "look at design-system conformance on the page" → audited: guardrails/colors/logical-direction/hooks/tooltip-placement all pass, `LabeledControl` confirmed as the page's shared field primitive (kit `Field` is not exported — DEC-10, reported for coordination with the scheduler-layout branch), and three real visual defects found by rendering at 390/768/1280 were fixed. [generalizable: yes — run the design-system linters AND look at a populated render at 390px; the linters passed on all three defects that only a render exposed]
- **FB-6** [status: resolved] — "write up why our current tests/gallery/rig did not catch these" → `TEST_GAP_ANALYSIS.md`. [generalizable: yes — when a defect reaches the owner, the analysis of which gate should have caught it is a deliverable equal in weight to the fix]
